# Выкат SEO-релиза: reg.ru + HostVDS

Дата: 2026-09-13. Пакет: `deploy/primcom-seo-20260814/`.

## 1. Фактическая схема

| Что | Адрес | Доступ | Что лежит |
|---|---|---|---|
| Сайт `primcom.ru` | `31.31.197.47` | reg.ru, SFTP/FTP | статические файлы, document root |
| Backend `api.primcom.ru` | `168.222.194.128` | `ssh root@168.222.194.128` | `/opt/primcom/china_cars_backend` |
| Telegram-боты | `213.232.204.127` | `ssh root@213.232.204.127` | `/opt/primcom/manager-listings-bot` |

Проверено 2026-09-13 через DNS. Сайт и backend — **разные машины**.

`BACKEND_RUNBOOK.md` до этой даты утверждал, что каталог сайта лежит на `168.222.194.128`.
Это неверно и приводило к неправильному плану выката.

## 2. Ограничение, которое меняет план

`scripts/publish-seo-catalog.mjs` пишет в **локальную** файловую систему:
создаёт временную папку внутри `PRIMCOM_SITE_ROOT` и делает атомарный `rename`
(`publish-seo-catalog.mjs:36`, `:75`, `:94`).

Значит автопубликация работает, только когда Node запущен на той же машине, где лежит сайт.
Сейчас Node и backend на HostVDS, а сайт на reg.ru, поэтому:

> **`SEO_PUBLISH_COMMAND` оставляем пустой.** Включать его в текущей схеме нельзя:
> публикатор либо перезапишет несуществующий путь, либо соберёт страницы на сервере,
> где их никто не отдаёт.

Инструкция из `deploy/primcom-seo-20260814/DEPLOY.md` написана в расчёте на один VPS
(`rsync` в `$SITE_ROOT`, `systemctl`). Для reg.ru она применима только частично —
раздел «Полное обновление», шаги 3–6, не выполняются.

## 3. Этап 1: сайт на reg.ru — главное

Этот этап и даёт весь SEO-эффект: 45 URL в sitemap превращаются в 141,
появляются 130 индексируемых страниц.

### 3.1 Резервная копия

Скачать текущий document root целиком по SFTP перед любой заливкой.
Без рабочего бэкапа дальше не идти.

### 3.2 Что заливать

Содержимое `deploy/primcom-seo-20260814/site/` — 191 файл, 16 МБ.
Заливать **целиком, с перезаписью, без удаления серверных файлов**.

Типовой document root на reg.ru:

```
/var/www/uXXXXXXX/data/www/primcom.ru/
```

Точный путь виден в панели reg.ru, раздел «Сайты» → домен → «Корневая директория».

Порядок внутри заливки важен только в одном месте: `sitemap.xml` заливать **последним**,
после `cars/` и `guides/`. Иначе поисковый робот может прийти по новому URL раньше,
чем появится страница.

### 3.3 Почему целиком, а не минимальный список

Минимальный вариант из `DEPLOY.md` допустим только если на сервере уже стоит июльский
пакет с ссылками на `/cars/` и `/guides/` в шапке и подвале. Проверить это по SFTP —
скачать `components/header.html` и `components/footer.html` и найти `href="./cars/"`.
Если хотя бы в одном нет, минимальный вариант ломает навигацию.
Заливка целиком снимает вопрос и стоит 16 МБ.

### 3.4 Приёмка

```bash
curl -I https://primcom.ru/
curl -I https://primcom.ru/cars/
curl -I https://primcom.ru/cars/japan/toyota/
curl -I https://primcom.ru/guides/
curl -s https://primcom.ru/sitemap.xml | grep -c '<loc>'
```

Ожидаемо: четыре раза `200`, затем `141`.

Дополнительно убедиться, что служебные dot-файлы не отдаются:

```bash
curl -I https://primcom.ru/.primcom-seo-publish.lock
```

Ожидаемо `403` или `404`.

### 3.5 После заливки

Отправить новый sitemap на переобход:

- Яндекс.Вебмастер → «Индексирование» → «Файлы Sitemap» → добавить `https://primcom.ru/sitemap.xml`;
- Google Search Console → «Файлы Sitemap» → тот же адрес.

GSC сейчас не подключён. Это отдельная задача, и до неё работа по реальным запросам невозможна.

## 4. Этап 2: backend и бот — можно отложить

Три файла backend (`app/api/routes.py`, `app/core/settings.py`, `app/services/seo_publish.py`)
и `manager-listings-bot/main.py` нужны **только** для автопубликации.
Пока `SEO_PUBLISH_COMMAND` пуст, они не дают ничего полезного, но добавляют шум:

при каждом сохранении карточки менеджер увидит

> SEO-страница не обновлена; карточка каталога сохранена. Автопубликация SEO не настроена на сервере.

Источник: `manager-listings-bot/main.py:728` и `seo_publish.py:98`.

**Рекомендация: этап 2 не выполнять**, пока не решён вопрос из раздела 6.
Сайт от этого не страдает — этап 1 самодостаточен.

Если всё же выкатывать (например, чтобы не расходиться с репозиторием):

```bash
# backend, 168.222.194.128
systemctl list-units --type=service --state=running | grep -E 'primcom-api(-v2)?\.service'
rsync -a /tmp/primcom-seo-20260814/backend/ /opt/primcom/china_cars_backend/
systemctl restart primcom-api.service
journalctl -u primcom-api.service -n 100 --no-pager
```

```bash
# боты, 213.232.204.127
cp /tmp/primcom-seo-20260814/manager-listings-bot/main.py /opt/primcom/manager-listings-bot/main.py
systemctl restart primcom-manager-listings-bot.service
journalctl -u primcom-manager-listings-bot.service -n 100 --no-pager
```

Если запущен `primcom-api-v2.service`, перезапускать именно его.
Миграция базы и перезапуск скрейперов не требуются.

## 5. Промежуточный процесс обновления страниц

Пока автопубликации нет, модельные страницы обновляются вручную с рабочей машины.
После заметного изменения каталога:

```bash
cd "/Volumes/SID/Колян АВТО/CSS&HTML Site"
node scripts/publish-seo-catalog.mjs
node scripts/check-seo-pages.mjs
```

Публикатор сам сходит в `https://api.primcom.ru`, пересоберёт `cars/`, `guides/`,
`sitemap.xml` и реестр, прогонит QA и заменит файлы атомарно.
Если каталог внезапно опустел, сборка упадёт с `catalog shrink guard` и ничего не тронет —
это защита, а не ошибка.

Затем залить на reg.ru по SFTP только изменившееся: `cars/`, `guides/`, `sitemap.xml`.

Разумная частота — раз в неделю или после крупного пополнения склада.

## 6. Как включить автопубликацию по-настоящему

Три варианта, от дешёвого к правильному.

**А. Публикатор на reg.ru.** Требуется SSH и Node на тарифе. На shared-хостинге reg.ru
SSH обычно есть, Node — не всегда. Проверить: `ssh` в аккаунт, затем `node -v`.
Backend тогда дёргает публикацию по SSH, а не локально — это доработка `seo_publish.py`.

**Б. Публикатор на HostVDS + шаг выгрузки.** Собирать в staging-папку на `168.222.194.128`,
затем `lftp`/`rsync` по SFTP на reg.ru. Атомарность на стороне reg.ru теряется:
во время выгрузки сайт какое-то время в смешанном состоянии. Нужна доработка публикатора.

**В. Перенести сайт на `168.222.194.128`.** Там уже есть nginx. Тогда вся текущая
архитектура работает как задумано, без единой правки кода. Меняются DNS и схема хостинга.

Вариант В — единственный, где ничего не дописывается. Вариант Б — самый быстрый по срокам.

## 7. Откат

Сайт: залить обратно скачанную в п. 3.1 резервную копию.
Backend и бот: вернуть предыдущие файлы и перезапустить те же два юнита.
База данных не затрагивается ни на одном этапе, откат безопасен.
