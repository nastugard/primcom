# Автопубликация: карточка из бота попадает на сайт без ручной пересборки

## Что происходит

1. Менеджер сохраняет карточку через бота.
2. Backend после сохранения запускает команду из `SEO_PUBLISH_COMMAND`.
3. Команда забирает актуальный каталог из API, собирает страницы моделей, разделы марок,
   `sitemap.xml`, проверяет результат и отправляет на хостинг **только изменившиеся файлы**.
4. Бот сообщает менеджеру «SEO-страница опубликована» или «обновлена» и показывает адрес.

Всё это уже написано и проверено. Не хватает одного: чтобы команда работала там,
где есть и Node.js, и доступ к хостингу. Это зависит от вашего хостинга.

## Как выбрать вариант

Сайт лежит на reg.ru, backend — на HostVDS. Публикатору нужно записать файлы туда, где живёт сайт.

| | Вариант А: публикатор на reg.ru | Вариант Б: сборка на HostVDS, отправка на reg.ru |
|---|---|---|
| Что нужно от хостинга | SSH и Node.js 18+ на тарифе | только FTP или SFTP |
| Как проверить | `ssh` в аккаунт и `node -v` | данные FTP из панели reg.ru |
| Что запускает сборку | cron на reg.ru раз в 15–60 минут | backend сразу после карточки |
| Задержка | до интервала cron | секунды |
| Статус в боте | не показывает результат | показывает |
| Сложность | меньше | чуть больше |

**Сначала проверьте вариант А:** зайдите по SSH в аккаунт reg.ru и выполните `node -v`.
На обычном виртуальном хостинге Node.js часто нет. Если его нет, берите вариант Б: он
работает с любым хостингом, где есть FTP.

---

## Вариант Б: сборка на сервере, отправка по FTP или SFTP

Выполняется на сервере, где работает backend (`ssh root@168.222.194.128`).
Нужны: Node.js 18+ и `lftp`.

```bash
node -v                 # должно быть v18 и выше
apt install -y lftp     # если lftp нет
```

### 1. Разложить файлы

Папку `seo-publisher-ГГГГММДД`, которую даёт `bash scripts/build-publisher-bundle.sh`,
загрузить на сервер:

```bash
mkdir -p /opt/primcom/seo-publisher
rsync -a seo-publisher-ГГГГММДД/ /opt/primcom/seo-publisher/
```

В ней: `scripts/` (публикатор), `seo/` (реестр и состояние дат), `site-staging/`
(полная копия сайта для проверки качества) и `sync.env.example`.

### 2. Настройки отправки

```bash
cd /opt/primcom/seo-publisher
cp sync.env.example sync.env
chmod 600 sync.env
nano sync.env
```

Заполнить `SYNC_HOST`, `SYNC_USER`, `SYNC_PASSWORD`, `SYNC_PROTOCOL` и `SYNC_REMOTE_ROOT`
(корень сайта относительно входа по FTP, его видно в панели reg.ru). Файл содержит
пароль: он не должен попасть в git и в чужие руки.

### 3. Проверить вручную, не отправляя ничего

```bash
cd /opt/primcom/seo-publisher
PRIMCOM_SITE_ROOT=/opt/primcom/seo-publisher/site-staging \
  node scripts/publish-seo-catalog.mjs          # собирает и проверяет
PRIMCOM_SITE_ROOT=/opt/primcom/seo-publisher/site-staging \
  node scripts/sync-to-host.mjs --dry-run       # показывает, что бы ушло, пароль скрыт
```

### 4. Первая настоящая отправка

```bash
PRIMCOM_SITE_ROOT=/opt/primcom/seo-publisher/site-staging \
  node scripts/publish-and-sync.mjs
```

Первый запуск отправит все страницы каталога (около 145 файлов), следующие — только изменения.
Затем:

```bash
curl -s https://primcom.ru/sitemap.xml | grep -c '<loc>'
```

### 5. Включить в backend

В `/opt/primcom/china_cars_backend/.env`:

```dotenv
SEO_PUBLISH_COMMAND=/usr/bin/node /opt/primcom/seo-publisher/scripts/publish-and-sync.mjs
SEO_PUBLISH_WORKDIR=/opt/primcom/seo-publisher
SEO_PUBLISH_TIMEOUT_SECONDS=120
PRIMCOM_SITE_ROOT=/opt/primcom/seo-publisher/site-staging
```

Таймаут 120, а не 90: сборка забирает каталог по сети и отправляет файлы по FTP.
Больше ставить нельзя: клиент бота ждёт ответа backend 180 секунд (`manager-listings-bot/main.py`),
и в этот запрос входит ещё загрузка фото. При таймауте выше бот показал бы менеджеру ошибку,
хотя карточка уже сохранена.
Затем `systemctl restart primcom-api.service` (или `-v2`, если работает он).

### 6. Проверка на живой карточке

Создать через бота тестовую карточку и убедиться, что бот пишет «SEO-страница опубликована»,
а страница модели на сайте показывает новую строку в таблице.

## Вариант А: публикатор прямо на хостинге

Только если на reg.ru есть SSH и Node.js. Тогда отправка не нужна: публикатор пишет
в папку сайта сам.

```bash
# на reg.ru, в домашней папке
mkdir -p ~/seo-publisher && rsync -a seo-publisher-ГГГГММДД/scripts seo ~/seo-publisher/
```

Проверить один раз вручную, указав настоящую папку сайта:

```bash
cd ~/seo-publisher
PRIMCOM_SITE_ROOT=/путь/к/папке/сайта node scripts/publish-seo-catalog.mjs
```

Затем cron (в панели reg.ru или `crontab -e`), например каждые 20 минут:

```
*/20 * * * * cd ~/seo-publisher && PRIMCOM_SITE_ROOT=/путь/к/папке/сайта /usr/bin/node scripts/publish-seo-catalog.mjs >> ~/seo-publisher/cron.log 2>&1
```

В этом варианте `SEO_PUBLISH_COMMAND` в backend остаётся пустым, а бот не показывает
результат публикации.

## Что защищает от поломок

- **Страницы не заменяются, если сборка не прошла проверку.** Сборка идёт во временной
  папке, заменяются файлы атомарно, при ошибке остаётся прежняя версия.
- **Защита от опустевшего каталога.** Если API вернул подозрительно мало карточек,
  сборка падает и ничего не снимает с индекса (`SEO_MIN_ACTIVE_RATIO`).
- **Защита от массового удаления на хосте.** Если к удалению больше 20% файлов, отправка
  останавливается (`SYNC_ALLOW_MASS_DELETE=1` — для намеренного случая).
- **Сборка и отправка под одной блокировкой.** Вторая карточка, сохранённая сразу
  после первой, ждёт очереди и не читает файлы посреди пересборки.
- **Отправка идемпотентна.** Если связь оборвалась на середине, следующий запуск
  повторит недоотправленное. Изменение считается по содержимому, а не по размеру:
  правка цены с 830 000 на 850 000 не меняет размер файла, но будет замечена.
- **`sitemap.xml` уходит последним:** робот не увидит адрес раньше страницы.

## Даты: почему страница «не обновляется каждый день»

`lastmod` в sitemap и надпись «Данные обновлены» на странице меняются, **только когда
изменилась сама страница**. Раньше всем страницам ставилась дата запуска, и sitemap
сообщал поисковикам, что за день изменилось всё. При автопубликации это происходило
бы после каждой карточки. Теперь состояние хранится в `seo/lastmod-state.json`:
пересборка при неизменном каталоге не меняет ни одного файла.

## После каждого релиза фронтенда

Копия сайта `site-staging/` нужна проверке качества, поэтому после изменения CSS, JS
или страниц её надо обновить: заново собрать папку `bash scripts/build-publisher-bundle.sh`
и загрузить `site-staging/` на сервер. Версия ресурсов в собираемых страницах
берётся из `site-staging/index.html` сама.

## Чего здесь нет

Отправка на настоящий FTP или SFTP-сервер проверена только в режиме `--dry-run` и на
локальном транспорте: реального сервера reg.ru у меня нет. Поэтому первый запуск
нужно делать вручную (шаги 3–4), а не сразу через backend.
